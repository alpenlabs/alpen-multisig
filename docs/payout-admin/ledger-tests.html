Payout Administrator · regtest · physical Ledger

Physical Ledger test guide

Run each case on real hardware. Compare the device with the app before approving. Reference images are emulator captures, never evidence of a physical pass.

Rules before starting

  • Use regtest only and the device’s own existing seed. Never reset it or load the Speculos seed. Close Ledger Live and other USB clients.
  • Unlock and open Bitcoin Test before connecting. Use 2.4.6 or later. Test 2.4.6 and 2.5.1 on compatible devices separately. Record unsupported combinations as BLOCKED. Do not assume a later version has identical screens; the app flags versions beyond those checked.
  • Never enter the PIN while the desktop app or a test is talking to the Ledger. If it locks, wait for the request to fail or stop the app. Unlock only after device I/O stops. Then reopen Bitcoin Test, reconnect and review again.
  • Before long tests, set a longer PIN-lock interval while idle, or keep the device awake with occasional button activity. Never use blind approval. Restore the previous lock setting after testing.
  • Record device model, device OS, Bitcoin Test app version, host OS, desktop commit/build, date, tester, claim count, covenants and timings. Photograph every screen that differs from this guide and the app checklist. Never photograph a PIN or seed.
  • Approve only when every value is readable and matches. A blank value on a physical device means reject. Navigate with left/right; on Nano X / S+ both buttons approve the displayed action. Other models may use different controls.

Setup and evidence baseline

Follow setup.html for binaries, Bitcoin Core with txindex, coordinator, regtest deployment built from your Ledger’s public identity, roster, confirmed funding and report seeding. Follow guide.html for UI navigation. This guide starts no Docker services. Run only one hardware client at a time.

For supplemental hardware-only multi-covenant coverage, the existing e2e_payout_claims_matrix harness can use the physical Ledger’s identity unchanged. With the desktop closed, Bitcoin Test ready and LEDGER_SPECULOS_URL unset, a tester can run LEDGER_PHYSICAL=1 CLAIM_COUNT=6 COVENANTS=3 cargo test -p alpen-multisig-e2e-tests --test e2e_payout_claims_matrix -- --nocapture. Use COVENANTS=2 for two covenants. It starts isolated Bitcoin Core and coordinator processes, not Docker. It directly funds connectors, so this is supplemental device evidence, not a substitute for the UI/report-verification cases. Attach its MATRIX_RESULT output separately.

Prepare independent fresh claims and funded coins for each success case. The seeder adds new claims on every run with the same output directory: set PAYOUT_SEED_CLAIMS to the number you need, for example PAYOUT_SEED_CLAIMS=120 before L08 to L12 (1 + 2 + 4 + 8 + 90 claims plus spares), and paste the new reports.json. A spent claim cannot be reused. Keep the same app profile for registration-cache tests. Record policy names and covenant membership. The seed count alone does not prove multiple covenants: require a fixture whose params and reports actually span them.

Regtest uses path m/86'/1'/73' and unit TEST. Bitcoin Test displays testnet address encodings (tb1… for witness outputs); the app uses bcrt1… and supplies the device form for comparison. Compare the full device form, not just a changed prefix or checksum. The backend checks address equivalence. Example amounts, nonces, keys and policy IDs in the images are not your fixture values.

The current spec records a hand run on 2026-11-13: Nano X, OS 2.7.0, Bitcoin Test 2.4.6, sign-in, Show on Ledger and 1, 4, 10, 20 and 90 claims accepted by Core. Older runbook §6/§8 and compliance M2 still say pending. The current spec supersedes those status statements. Several covenants, rejection and unplug remain unverified physically there. Emulator coverage includes Nano X and Nano S+, 2.4.6 and 2.5.1. Do not prefill any new physical result as PASS.

External inputs are expected only in payout passes. Each pass signs one policy’s inputs. Other covenants and fee coins are external in a claim pass; all claims are external in the fee pass. Fees is always the whole transaction fee, not an extra fee per pass. On 2.5+, each claim contributes 330 sat to its covenant’s You spend. The fee pass may say You receive when claim value exceeds the fee. On 2.4.x it is a 0 TEST self-transfer. Compare actual checklist values before choosing Continue anyway.

L01. Open app and version check

PRD 06 §3.b.i, §3.b.iv

Preconditions. Ledger idle, own seed unchanged; compatible versions available on test devices. Do not downgrade a device just to obtain an old version.

  1. Close Ledger Live. Unlock while the desktop is idle. Open Bitcoin Test 2.4.6 or later and click Connect Ledger. Record the reported version.
  2. Disconnect in the UI. Repeat with the wrong app open, then an available Bitcoin Test older than 2.4.6. If no old app is available, mark that variant BLOCKED.
  3. Sign in with the supported app. When idle, close Bitcoin Test, then request a payout checklist. Reopen it and reconnect. If testing a different version, sign in again.

Device screens, in order

Supported app: Bitcoin Test ready screen; no signing approval during version detection. Wrong or closed app: no valid payout review. Too old: no signing request. Ready-screen wording depends on device firmware.

App at the same time. Connect reads GET_VERSION. Wrong app asks to open Bitcoin Test. Too old asks to update to 2.4.6 or later. Closed app produces an error. A changed version before review or signing requires a new sign-in.

Pass criteria

  • Supported version matches the device.
  • Wrong, old and closed-app variants never sign.
  • Recovery succeeds; a different version does not use the old checklist.

L08. Payout with 1 claim

PRD 06 §6.d.ii–vi, §3.b.iv

Preconditions. 1 fresh valid claims from one covenant, 2-of-3 deployment, confirmed unreserved Admin Wallet funds. Use setup.html to seed the required count.

  1. Paste reports and retain exactly 1 claim inputs. Set a fee rate, record txid, size, fee, input total and change. Ensure the plan contains one transaction.
  2. Open the checklist; record any registration and perform L07 if needed. Click Confirm.
  3. Compare and approve the claim pass, then the fee pass below. Measure each loading/signing interval.
  4. Check Pending for your signature. Have another admin sign to quorum, then verify node acceptance and Past status.

Device screens, in order

Claim pass

Bitcoin Test 2.4.x Bitcoin Test 2.5+

Security risk → There are external inputs / Reject if not sure → Continue anyway → Review transaction / to send bitcoin → From: Payout <id> → Amount: change value → To: change address, all pages → Fees: whole transaction fee → Sign transaction → Transaction signed.

Security risk → There are external inputs / Reject if not sure → Continue anyway → Review transaction / to send bitcoin → From account: Payout <id> → Amount: change value → To: change address, all pages → External amounts: all inputs outside this covenant → You spend: this covenant’s claim input total → Fees: whole transaction fee → Sign transaction → Transaction signed.

Fee pass

Bitcoin Test 2.4.x Bitcoin Test 2.5+

Security risk → There are external inputs / Reject if not sure → Continue anyway → Review transaction / to send bitcoin → Amount: 0 TEST (self-transfer) → Fees: whole transaction fee → Sign transaction → Transaction signed.

Security risk → There are external inputs / Reject if not sure → Continue anyway → Review transaction / to send bitcoin → External amounts: all claim inputs → You spend: fee inputs minus change; or You receive: change minus fee inputs → Fees: whole transaction fee → Sign transaction → Transaction signed.

App at the same time. The checklist lists this transaction’s actual values, fee and destination. Pending shows Signed and quorum progress; at quorum the app broadcasts. Failed broadcast stays Pending with Retry broadcast.

Timing baseline for Nano X 2.4.6: claim loading 4 + 2.0 × 1 = 6 s; claim signing 1.9 × 1 = 1.9 s; fee-pass loading 3 + 1.3 × 1 = 4.3 s. Excludes human review, registration and final fee signing. Record measured times, not a timeout pass/fail threshold.

Report results and limitations

Copy ledger-results.csv to a dated result file and fill one row per case, device/app combination and variant. Use PASS, FAIL, BLOCKED or NOT RUN; L02 is an accepted gap, not a PRD pass. Also fill or print the result box beside each case. Attach full device photos, matching UI checklist captures, timings by pass, sanitized app/test logs, txids and Core acceptance/confirmation evidence. For a failure give the last successful screen, exact error (including 0x6a80), whether Bitcoin Test exited or locked, and recovery steps. Preserve results from failed attempts.

Attach build commit, fixture report identifiers and deployment fingerprint. Do not attach seeds, private keys, PINs, RPC passwords or coordinator tokens. Send the bundle to the test coordinator with the failing case IDs. A case without fixtures or a compatible device is BLOCKED, not skipped silently.

Known emulator artefact. Emulated 2.4.6 images show blank Amount, To and Fees in payout reviews. The wallet send and bump logs also show bare labels on emulated 2.4.6. Physical Nano X 2.4.6 payout values were readable in the recorded run. Never accept a blank physical screen on the strength of these images. Wallet logs on 2.5.1 show Amount 0.0002 TEST, Fees 0.00000308 TEST for send and 0.0000077 TEST for bump; these are examples only. An initial Message signed or Transaction signed in those logs belongs to the preceding operation.
Requirement gaps and boundaries
  • D5: no Payout Admin ID display, certificate signing/copy or verify-on-device before or after sign-in. L02 records this gap.
  • D6: no fee bump for payout transactions. L21 applies only to own Admin Wallet sends.
  • D7: TRUC 10,000 vB; 90 claims is the reference 2-of-3 capacity, not universal across input shapes.
  • D9: incoming unconfirmed receives are not shown; address rotation waits for confirmation.
  • D11: no P2PK destination address exists; test the five address types in L18.
  • Ledger only. Trezor and BitBox are unsupported by this slice.
  • Export/import, paste signatures, retry broadcast and rebroadcast use already produced signatures. They introduce no device review. Check their UI behavior in guide.html.
